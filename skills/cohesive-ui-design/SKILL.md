# 一体化 UI 设计

把个人审美转化为可迁移的设计判断。目标是让页面在静止时有完整的秩序，操作时出现贴合内容的反馈，细节能够经得起停留和反复使用。

本 Skill 提供审美与取舍标准，可与 `frontend-design` 或项目已有设计系统配合，也能独立使用。用户当前明确的品牌、布局、主题和改动范围优先。没有规定所有项目使用同一配色、字体、圆角或动效。

## 先建立这次任务的边界

从现有页面、需求和对话中确定：谁在使用、主要任务、品牌依据、最重要的入口、用户已认可的部分，以及本次允许改动的范围。已有答案直接采用，不重复询问；只有缺失信息会改变设计方向时才澄清。

- 用户只要求修局部时，先保留布局、内容、业务行为和已接受的效果。
- 全面改版时可以重组布局；局部修饰无法解决真实的信息结构问题时，先说明原因，再在已授权范围内处理。
- 重构前检查 Git 状态；已有可用提交可以作为回退点，未提交的本次范围改动先按用户要求保存。保护无关工作，不把 UI 优化扩大为认证、数据或部署变更。
- 方案评估只交付评估；实现、发布和同步分别依据现有授权继续，不额外创造重复审批。

## 稳定偏好

### 1. 先让整体成立，再打磨局部

先看页面的共享背景、对齐轴、阅读顺序、留白节奏和交互范围，再看单个组件。关联区域可以通过共同底面、连续规则线、材质或状态反馈形成整体，避免每块都像独立贴上的卡片。

视觉连续不等于取消分组。保留导航、内容、操作和不同任务之间必要的边界。一体化装饰只能覆盖同一语义区域，不能顺势铺到无关表格、表单或正文背后。

遇到“割裂”时，优先检查容器内边距、背景叠层、蒙版、裁剪边界、伪元素、坐标系和事件覆盖范围。不要立即用更强的颜色或更多装饰掩盖接缝。

### 2. 让品牌色有重点，让中性色有设计

企业工具在没有其他要求时，可从浅色中性基底出发；用底面差异、字体层级、细边界、少量有意义的细节消除空白的平庸感。纯白、浅灰和品牌色各自承担角色。

品牌色在主要操作、选中状态、重点图形等位置可以明确鲜明。通过面积、位置和频率控制整体强度，避免把所有区域都染成淡淡的品牌色。也不要为了“高级”把重要操作降低到难以识别。

用户指定深色、其他主色或已有成熟设计系统时，沿用它们来表达上述关系。状态色、图表分类色和警示色保留业务语义。白银灰与红色只是一个成功案例，不是通用色板。

### 3. 细节来自主题，先帮助理解

从真实内容中选择少量设计依据，例如资料的分层、编辑工作的修订关系、设备的信号路径、展品的材质。提取其组织和交互逻辑，不把整套现实物件塞进界面。

装饰要有轻重和疏密。主要关系完整清楚，辅助细节留在适当位置；空白可以用于缓冲，不必全部填满。不要用一串没有产品意义的技术标签证明专业，也不要把所有元素排成重复成套的小花纹。

精简装饰不等于删减业务信息。地图真实路线、图表曲线、流程拓扑和告警都属于内容，不能为了清爽随意减少、断开或弱化。

字体、间距、边缘处理和状态衔接同样可以承载巧思。不要求每个页面都有一个发光图形。

### 4. 信息顺序服务使用路径

先让用户知道这里能做什么、如何进入主要任务。多工具门户的统一介绍可以放在具体功能之前，并在首次进入时默认展示；工具入口仍应容易发现和直接使用。

熟练用户的管理后台、告警台、编辑器和高频工作流，优先呈现当前任务与必要信息，帮助入口按需出现。不要把“快速上手第一项”固化成所有产品的导航规则。

轮播只是已有内容的一种承载方式，不主动用轮播替代清晰的入口；采用时保留可直接选择的选项、手动控制与暂停能力。

### 5. 交互有回应，环境动效有节制

把“有一点炫技”落实为反馈准确、过渡连续、状态切换有细节。先定义用户做什么、哪个对象响应、反馈说明了什么，再选动画技术。

- 无操作时，页面的阅读和操作优先。展示区可以有缓慢、低对比的环境运动；高密度任务区可以完全静止。
- 悬停、键盘聚焦或选择时，提高相关对象的存在感，并弱化同区域的无关运动。
- 选项、列表与上方展示有关联时，让反馈去往对应对象，而非机械地停留在鼠标处。
- 目标改变时从当前视觉状态平滑过渡，离开时自然恢复；快速往返、连续切换和中途打断不应跳变或残留。
- 触屏不依赖悬停，重要反馈不依赖动画；减少动态效果时保留可见的静态选中状态。

需要光团、聚焦和关联线条时，读 [交互做法](references/interaction-recipes.md)。这些是条件式做法，不是每次设计的必选元素。

## 把反馈转成可验证的改动

用户的直觉描述通常指出症状，也可能包含一个试探性的方案。保留目标，允许换用更合适的实现；不要把每次试探都累积成永久规则。判断有冲突时，读 [偏好来源与诊断](references/preference-model.md)。

1. 找到最影响观感的问题。区分结构、色彩面积、层次衔接和运动状态，不同时试改所有维度。
2. 用简短的话给出本次判断与选择。例如“底面被切成两块，先统一背景和交互范围，再看是否还需要增强光效”。
3. 复用项目组件和现有技术。先修结构、状态与图层责任；避免不断叠加覆盖样式、重复图层或为细小效果引入大型依赖。
4. 检查正常态、交互态和过渡态。静态截图无法证明动画自然；构建通过也不能代替视觉判断。
5. 只根据真实反馈和发现继续迭代。已经成立的部分保持稳定，避免修一个局部又破坏上一轮认可的效果。

不熟悉的产品类型读 [跨场景取舍](references/scenario-adaptation.md)，确定哪些偏好保持、哪些手法应替换或省略。不要照搬原项目的布局和视觉符号。

## 验收与交付

根据本次改动选择必要检查，不为简单调整建立庞大测试流程。

- 整体：缩小看是否有清晰重点，正常尺寸看文字是否舒适；同一视觉区域有无白缝、硬切边或不一致的背景。
- 操作：主入口易找且能用；选中、悬停、键盘聚焦之间的含义清楚，反馈对应正确对象。
- 动态：看进入、移动、切换、离开与中断；检查叠色、闪烁、瞬移、遮字、交互死区和失控的背景运动。
- 适配：在目标桌面和窄屏视口检查重排、触屏与键盘路径；涉及动画时检查减少动态效果、离屏/后台暂停和卸载清理。
- 功能：验证受影响的现有行为。引用真实测试结果，不把审美接受程度转换成虚假的通过分数。

交付说明这次改了什么、为什么更符合使用场景、实际验证了什么，并给出可用预览或文件。清楚区分方案、已实现、本地验证、用户认可和已部署。
